## 2. Замеренные факты о git

Здесь дороже всего далось знание, а не код. Всё на **git 2.53.0.windows.3**.

**Какой хук ловит какой путь создания коммита.** Проверено хуком-отказником:

| путь | что срабатывает |
|---|---|
| обычный `git commit` | `pre-commit` |
| `git commit --amend` | `pre-commit` |
| `git merge --squash` + commit | `pre-commit` |
| `git merge --no-ff` | **`pre-merge-commit`**, `pre-commit` не зовётся никогда |
| `git cherry-pick` | только `prepare-commit-msg` и `post-commit` |
| `git revert` | только `prepare-commit-msg` и `post-commit` |

`cherry-pick` и `revert` **не покрыты и покрыты быть не могут дёшево**:
`post-commit` отменять не умеет, а `prepare-commit-msg` умеет (проверено — exit 1
отменяет обе операции), но получает `$2 = message` и на обычном коммите тоже,
различить пути нельзя. Гейт гонялся бы дважды на каждом коммите.

**Нормализация CRLF.** `git add --renormalize . && git checkout -- .` — **no-op**.
`--renormalize` оставляет stat-кэш индекса совпадающим с CRLF-файлом, и `checkout`
считает файл актуальным. То же бездействие у `checkout -f`, `restore --worktree
--source=:0`, `checkout-index -f -a` и круга через `stash`, при `core.autocrlf`
и `true`, и `false`. Переписывает только удаление файлов перед checkout. Рабочий
ответ для Go — `gofmt -w .`: он же и жалуется, всегда пишет LF, а следующий
`git add` нормализует индекс.

**`git check-ignore`.** Exit 0 = игнорируется, 1 = нет, 128 = не репозиторий (не
доказательство ничего). Отвечает и на каталоги, включая вложенные на несколько
уровней внутрь игнорируемого. Батч через `--stdin` **непригоден**: git C-квотирует
любой путь с обратным слэшем (`"C:\\dir\\f.gd"` плюс хвостовой CR), а `-z`, который
вернул бы их сырыми, переключает и **ввод** на NUL-разделение, чего конвейер
PowerShell не даёт. Отсюда exit-коды, а для godot — мемоизация по каталогам.

**Параллельные коммиты в одном дереве.** `.git/index.lock` **не существует**, пока
работает pre-commit — поллить нечего. Git сериализует финальную запись, но индекс не
защищает: A застейджил `a.txt`, во время его хука B сделал `git add b.txt`, коммит A
забрал **оба** и увёз `b.txt` внутри себя. B получил не `cannot lock ref`, а
`nothing to commit, working tree clean` — **сообщение формы успеха** для проглоченной
работы. Это и есть корень историй про снесённый лок и коммит из устаревшего индекса.

**`git write-tree`** стабилен через всё окно хука при незастейдженных правках и
активном stash от lefthook — поэтому страж индекса не даёт ложных отказов.
**`GIT_INDEX_FILE`** git выставляет своим хукам и больше никто: это признак «мы
внутри коммита».

## 3. Прочее замеренное

- **`lefthook` 2.1.12** резолвит YAML-якоря и ставит оба хука:
  `sync hooks: (pre-merge-commit, pre-commit)`.
- **`gofmt`** разворачивает однострочную функцию с длинным телом и требует таб —
  фикстура, не проходящая gofmt, роняет прогон **до** `go test`, из-за чего проверка
  «`[NOTE]` не появился» может пройти по чужой причине.
- **`errno=1455`** — не «кончилась RAM», а Windows про слишком маленький файл
  подкачки (лимит фиксации).
- **`GOTOOLCHAIN=auto`**: если директива `go` в go.mod новее установленного go,
  каждый вызов идёт через тулчейн из module cache. Параллельная сборка во время
  распаковки видит частично разложенное дерево std → «missing std package», **каждый
  раз другой пакет**. Не дефект гейта.
- Симуляция офлайна: `$env:HTTPS_PROXY='http://127.0.0.1:9'` детерминированно даёт
  `[UNKNOWN] could not check`.

## 4. Известные границы, выбранные осознанно

Это **не** недоделки — решения с причиной. Не «чинить» их не подумав.

- **`cherry-pick` / `revert` не покрыты гейтом.** Причина выше. Практический вывод:
  относиться к ним как к `--no-verify`.
- **Страж индекса не делает параллельные коммиты безопасными.** После отказа индекс
  всё ещё содержит оба набора изменений. Меняется одно: молчаливый неверный коммит
  становится отказом с названной причиной.
- **Гранулярность gitignore-фильтра для godot — каталог, не файл.** Правило,
  называющее отдельный `.gd` внутри отслеживаемого каталога, не учитывается. Цена за
  отказ от git-процесса на каждый файл.
- **Каталоги `quality-gate-build-*` от прежних версий в TEMP не подметаются** (на
  этой машине их было 731). Удалять файлы, которых прогон не создавал, — не дело
  гейта.
- **`wire` не перезаписывает существующий `lefthook.yml`.** Отличить старый шаблон от
  отредактированного вручную нельзя, поэтому он называет недостающий хук и печатает
  команду замены.
- **`-p`/`GOMAXPROCS` для race-фазы не ограничены.** Настройка под конкретный хост, а
  не свойство гейта.

  PreToolUse-хуком `graphify hook-guard` (140 мс на вызов, не блокирует, только
  подсказывает). Путь к `graphify.EXE` в settings абсолютный — на другой машине
  перезапустить `graphify claude install`.
- `graphify update` работает (exit 0, инкрементально). Что граф **не видит**: `.gd`,
  `.tscn`, `.godot`, `.proto`, `.toml`, `.cmd` — их нет в `CODE_EXTENSIONS` graphify

`1 collapsed (undirected) edge` — часть рёбер ссылается на узлы, которых нет
(семантическая выборка назвала сущность, которой AST не породил). Граф пригоден,
но это не полное отображение репозитория: узел, которого в графе нет, ещё не значит,
что его нет в коде. Спорные связи помечены `INFERRED` — проверять, а не верить.

---

## 6. Как проверять

```powershell
pwsh -NoProfile -File .\selftest.ps1
```

Онлайн ждать `all checks passed (168/168)` (или 167/167 с `[skip]` реестра cargo). Офлайн — меньше и `[skip]` с причиной;
это норма, а не регрессия. Блок dotnet требует SDK 8.x (`dotnet --list-sdks`), иначе
весь блок — `[skip]`.

Правило набора (его же заголовок, §0.1 PLAYBOOK): отрицательная проверка обязана
утверждать исход, сработавшую причину через `-match` **и** отсутствие
неприменившейся через `-notmatch`. За сессию трижды ловил себя на
**нефальсифицируемой** проверке — она проходила по причине, к предмету отношения не
имеющей. Если проверка не может упасть, она не покрытие.

## 7. Как работать со входящими отчётами

Отчёты приходят из соседних агентских сессий. За сессию их было семь.

**Симптом был верен всегда. Причина или предложенная команда — неверны в половине
случаев.** Опаснее всего готовая команда: она приходит в собранном виде и читается
как уже проверенная (`git add --renormalize` чуть не уехал дословно; поймал Codex).

Порядок: воспроизвести → прочитать источник → только потом править. И отписаться,
какая часть отчёта не подтвердилась, с замером — докладчик обычно действует на её
основании у себя.
