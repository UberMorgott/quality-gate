# Playbook: автоматический контроль качества и тесты, которые действительно ловят

Файл переносимый: языка и стека не предполагает. Отдать агенту целиком с задачей
«построй это у меня в проекте». Написан по итогам кампании, в которой закрыты все 946 замечаний
статического анализа (946 → 0) и попутно найдено около тридцати настоящих
ошибок, несколько — с последствиями для безопасности.

Всё, что здесь написано, оплачено набитыми шишками. Пункты со значком **⚠** — те, где
интуитивно правильное действие оказалось неправильным.

---

## 0. Главный вывод, ради которого стоит читать дальше

**Покрытие тестами меряет счастливые пути. Зелёный прогон тестов ничего не подтверждает.**

Проверка, которая это доказала: взять пакет с хорошим покрытием (60–77 %), сломать код так,
чтобы удалялся не тот каталог, прогнать весь набор тестов. Весь набор прошёл. Поломку не
заметил никто.

Почему так выходит. Строка считается покрытой, если она *исполнилась*, а не если её результат
*проверили*. Обработчик события регистрируется — строка зелёная, само событие в тестах не
наступает никогда. Функция записи файла при 75 % покрытия пакета не вызывается ни одним тестом.

**Следствия, из которых собран весь остальной документ:**

1. Первое, что надо сделать в чужом (и в своём) проекте — не писать тесты, а **проверить
   существующие мутацией**. Испортить одну ветку руками и посмотреть, кто это заметит.
2. Тест, который зелёный и до починки, и после — ничего не доказывает. Обязательна проверка
   **red-then-green**: откатить правку, убедиться что тест краснеет, вернуть правку.
3. Тесты пишутся не «на модуль», а **на те ветки ошибок, которые затрагивает конкретная
   правка**.

### 0.1 Верный исход не доказывает верную причину  ⚠

Продолжение того же вывода, оплаченное отдельно: пять issue подряд по этому же гейту, и каждый
дефект после первого был одной формы — **инструмент делал защитимое действие и печатал причину,
которая не была причиной**. Правка корневого файла расширяла прогон на все стеки (верно) и
объявляла `[WHY] proto changed`, хотя ни один `.proto` не менялся. Чистое дерево проверяло всё
(защитимо) и писало `not a git repository` внутри git-репозитория. Пустой путь в списке изменений
расширял прогон на первой же итерации, так что быстрый уровень **никогда** не сужался для правок
tracked-файлов — а вывод при этом выглядел разумно.

Ни один из них не был виден набору проверок, потому что набор проверял **исход**: упал ли стек,
какой exit code. Исход был правильным во всех случаях. Проверок не было на то, **какая ветка
выбрана** и **что именно напечатано как объяснение**.

**Правило.** Проверка отрицательного случая обязана утверждать три вещи, а не одну:

1. исход (exit code, упавшая фаза);
2. что напечатана причина, которая применилась (`-match`);
3. что причина, которая **не** применялась, отсутствует (`-notmatch`).

Третий пункт — тот, которого не хватало, и он же самый дешёвый: одна строка `-notmatch` ловит весь
класс «правильный результат по неправильной причине». Проверять надо и отсутствие, а не только
наличие: «сузилось до нужного стека» доказывается тем, что остальные стеки **не** запускались.

**Ловушка, специфичная для PowerShell** (две из пяти issue — она): пустое значение читается как
отсутствие. `@(...)` в конце функции возвращает пустой массив как `$null`, поэтому «нет правок» и
«не git-репозиторий» стали неразличимы; строка `"\r\n"` от `Out-String` непуста, проходит
`Where-Object { $_ }`, и только последующий `.Trim()` делает из неё `''`, после чего `if ($x)`
читает её как «ничего не было». Лечится унарной запятой (`,@(...)`), фильтрацией **после**
нормализации и сравнением `-ne $null` вместо проверки на истинность. Отдельного общего правила не
заслуживает — заслуживает по регрессионной проверке на каждый случай.

## 1. Порядок работ

Кампания устроена как конвейер, а не как разовая уборка.

```
гейт качества  →  измерить бэклог  →  очередь по модулям  →  один модуль за раз
   →  правка вместе с тестами  →  red-then-green  →  ревью вторым движком  →  коммит
```

Ключевое: **бэклог не чинится «сплошняком»**. Он режется на модули, модуль закрывается
целиком и после этого строгость на нём включается навсегда. Иначе через неделю в
почищенном месте снова свежие нарушения.

---

## 2. Гейт качества: одна точка входа

Один скрипт, который знает про все проверки. Не десять команд, которые надо помнить.

**Требования к нему, все из практики:**

- **Стоп на первой упавшей фазе.** Форматирование → сборка → статический анализ → линтеры →
  тесты. Смысла запускать тесты на несобирающемся коде нет, а вывод от этого нечитаемый.
- **Два уровня.** Быстрый (у нас 11 с) — на каждый ход агента. Полный (48 с) — перед коммитом.
  Разница почти целиком в сборке фронтенда: 36 с из 48. Замерьте свои фазы и вынесите
  самую дорогую в полный уровень, иначе гейт начнут отключать.
- **Определение стека по факту наличия файлов**, а не по конфигу. Есть `go.mod` → есть фазы Go.
  Есть `package.json` + конфиг сборщика → есть фронтенд. Нет признака — фазы не существует,
  ноль затрат. Для сборной солянки это единственный работающий подход.
  Различать два случая: «стека нет» — молча пропустить; «стек есть, а конфига линтера нет» —
  сказать один раз.
- **Автоопределение изменённой стороны** по состоянию системы контроля версий: правили только
  фронтенд — не гонять бэкенд.
- ⚠ **Линтер запускать без автоисправления.** Режим `--fix` прячет от вас то, что вы пришли
  посмотреть, и делает диффы агента непредсказуемыми.
- Один и тот же команда `qgate` вешается тремя способами: хук завершения хода агента, хук перед
  коммитом, шаг в CI. Три вызова, одна логика. Скрипты в целевой репозиторий не копируются —
  `qgate wire` записывает только конфигурацию.

**Зачем хук на завершение хода агента.** Он не даёт агенту закончить ход со сломанной сборкой.
Без него агент отчитывается «готово», а гейт красный.

⚠ **Проверьте, что хук реально исполняется.** У нас он неделю **молча пропускал проверку**:
в конфиге стоял относительный путь, а рабочий каталог не совпадал с корнем репозитория. Хук
«работал», ничего не проверяя. Путь задавать абсолютным (через переменную окружения с корнем
проекта), а после настройки — намеренно сломать код и убедиться, что хук ругается.

## 3. Механизм волн: очередь как часть конфига линтера

Когда включаешь строгие правила на старом проекте, находок сразу сотни. Обычная реакция —
выключить правило глобально, и оно уже не включится никогда.

Работающая схема:

- Строгие правила **включены на весь репозиторий**.
- Для каждого ещё не почищенного модуля в конфиге стоит **именное исключение** с путём,
  привязанным строго к файлам самого модуля, **без подкаталогов** (иначе чистка родителя
  молча снимает строгость с детей).
- Модуль почищен → его строка **удаляется** из конфига. Строгость на нём теперь навсегда,
  новое нарушение валит гейт.
- **Список только сокращается. Он и есть трекер прогресса.** Второго списка заводить не надо —
  он разойдётся с реальностью в первую же неделю.

Рядом со списком — комментарий с историей: сколько было в начале, что закрыто, сколько
осталось, и **почему** отложено то, что отложено. Через месяц никто не вспомнит.

**Порядок модулей в очереди — по убыванию количества находок**, но с одной поправкой: модуль
с нулевым покрытием тестами берётся не первым, для него сначала пишутся характеризующие тесты
(см. §5).

## 4. Категории находок и как их чинить

Формулировки под конкретный линтер подставите свои, суть переносится на любой язык.

### 4.1 Отменяемость (контекст / токен отмены / сигнал прерывания)

⚠ **Самая дорогая ошибка кампании — «починка», которая подставляет пустой контекст в место
вызова.** Линтер замолкает, работа остаётся неотменяемой, и теперь это выглядит починенным.
Хуже, чем было.

Правильно — **тащить настоящий контекст**: от входа (обработчик запроса) через слой сервиса
до обращения к базе, меняя сигнатуры и поправляя всех вызывающих. Это скучно и это работает.

Три ловушки, каждая стоила отдельного бага:

- ⚠ **Фоновая работа не должна брать контекст запроса.** Внутри замыкания фоновой задачи
  контекст запроса компилируется и проходит линтер, но убивает задачу ровно в тот момент,
  когда обработчик вернул ответ. У нас так чуть не умерли 11 фоновых заданий.
- ⚠ **Запись финального состояния должна быть отвязана от отмены.** Отметка «отменено /
  провалено / завершено», уборка, закрытие сессии, оповещение *других* пользователей — всё
  это на контексте без отмены с явным таймаутом. Иначе отменённое задание навсегда останется
  в статусе «выполняется», и интерфейс будет ждать его вечно.
- ⚠ **Таймаут финальной записи создавать *после* долгой операции, а не до.** У нас 10-секундный
  таймаут отвязанного контекста создавался перед запуском задания — и любое задание длиннее
  10 секунд (а это все загрузки) доходило до финальной записи с уже истёкшим контекстом.
  Ровно тот баг, от которого этот контекст и защищал. Нашло ревью вторым движком.
- ⚠ **Цикл, вышедший по отмене, не должен публиковать частичный результат.** Загрузка списка
  устройств прерывалась по таймауту и затирала полный кеш неполным, а операция при этом
  отчитывалась об успехе. Тоже нашло ревью.

Фоновой работе (планировщики, опрос, индексация, рассылка) — **явный ограниченный по времени
контекст, задокументированный у определения**. Не «где-то там разберутся».

### 4.2 Непроверенные ошибки

Классифицировать **каждое** место, вариантов ровно три: пробросить / залогировать и
деградировать / объединить с уже имеющейся ошибкой. Молча проглотить — не вариант.

Явное игнорирование допустимо только с комментарием-причиной в той же строке.

Что этот разбор реально нашёл:

- девять операций правки схемы падали молча — пользователь получал недонастроенную схему
  без единой строки в журнале;
- отказ чтения настроек превращался в пустой адрес сервера и всплывал далеко ниже как
  «соединение отвергнуто» — то есть диагностировался не там, где ломалось;
- утечка соединения и утечка сессии на внешнем сервере, потому что ошибку закрытия никто
  не смотрел;
- временные каталоги копились на диске незаметно.

Отдельные повторяющиеся классы, которые стоит искать целенаправленно:

- ⚠ **Цикл по результатам запроса без проверки ошибки итерации после цикла.** Список молча
  обрывается на середине и выглядит полным. У нас таких мест было девять в одном модуле.
- ⚠ **Потерянная ошибка закрытия файла при записи.** На заполненном диске получается обрезанный
  файл и «всё хорошо» в ответе.
- ⚠ **Запись в чужой массив при добавлении элемента** (aliasing среза/массива). Две штуки.

### 4.3 Непроверенные приведения типов

Решить, что происходит при неудаче. Всегда. У нас два таких приведения стояли внутри
критических секций и роняли обработчик запроса вместе с горутиной.

### 4.4 Перебор вариантов перечисления

⚠ **Нельзя закрывать пустой веткой «иначе».** Это ровно тот баг, который правило ловит:
новый вариант перечисления молча провалится в пустоту.

### 4.5 Безопасность

Это не шум линтера. Что нашлось у нас:

- **Обход пути с доступом на запись.** Идентификатор из URL попадал в склейку пути без
  проверки и доходил до операций записи.
  ⚠ Штатный разбор UUID оказался недостаточен: он принимает форму `{в фигурных скобках}` и
  с префиксом `urn:uuid:`, а **двоеточие в компоненте пути на Windows означает запись в
  альтернативный поток данных**. Нужна строгая проверка каноничной формы.
- **Ещё два непроверенных сегмента пути**, доходящие до записи: поле из ответа внешнего
  сервера (ему доверяли просто потому, что он «свой») и параметр маршрута, который потом
  передавался внешней утилите как аргумент командной строки.
- ⚠ **Порядок промежуточных обработчиков: аутентификация должна идти до проверки
  идентификатора.** При обратном порядке неавторизованный получает 400 вместо 401 и пишет
  запись в журнал — то есть может его засорять. Нашло ревью вторым движком, не человек.
- ⚠ **Ограничение на разбор формы ограничивает только память, файл пишется на диск целиком.**
  Нужно ограничивать само тело запроса. Классика, встретилась дважды.
- **Пароль/токен в сериализуемой структуре** — поле уезжало в ответ.
- **Переполнение при приведении целых.** Решить, что значит выход за диапазон: проверить и
  отвергнуть. Молчаливое заворачивание — это и есть тот баг, на который указывает линтер.
  У нас так номер процесса мог указать на *другой* процесс.

### 4.6 Подавление правил

Только с конкретной причиной в самой директиве. Настроить линтер так, чтобы **безымянное
подавление само было нарушением**. И ещё лучше — чтобы **устаревшее подавление** (правило уже
не срабатывает, а директива висит) тоже подсвечивалось: иначе они копятся как мусор.

## 5. Тесты: что именно писать

**Правило: правка и тесты на затронутые ветки ошибок — одна работа, не две.**

Минимальный набор на пакет:

- отказ хранилища;
- отмена контекста / прерывание;
- затронутые ветки авторизации (в том числе порядок: неавторизованный получает 401, а не 400,
  и **не** пишет запись в журнал);
- отвергнутый вредоносный ввод: `..`, абсолютный путь, `{скобки}`, префикс схемы, двоеточие;
- превышение размера тела запроса;
- значение вне диапазона.

**Проверка red-then-green — обязательная часть починки, а не формальность.** Хотя бы на одну
правку в пакете: откатить правку, показать, что тест падает, вернуть, показать, что проходит.
В отчёте — команда и обе строки. Без этого починка — ставка, а не починка.

**Модуль с нулевым покрытием.** Порядок инвертируется: сначала характеризующие тесты, которые
фиксируют текущее поведение затрагиваемых путей (это единственная страховка — больше нет
ничего), потом правки, потом тесты на новые ветки ошибок.

⚠ **Полезный приём: сделать константу таймаута переменной, чтобы тест мог её уменьшить.**
Иначе тест на «операция дольше таймаута» либо занимает десять секунд, либо не пишется вовсе.

Прогонять с перемешиванием порядка и без кеша (`-count=1 -shuffle=on` в терминах Go, у других
языков есть аналоги) — иначе тесты незаметно начинают зависеть от порядка.

## 6. Ревью вторым движком

**Каждый пакет после починки — на ревью другой модели**, отдельным процессом, по конкретному
коммиту.

Это не церемония. За кампанию второй движок нашёл **семь настоящих багов**, которых не увидел
ни автор правки, ни ревью первым движком. Самые показательные: порядок промежуточных
обработчиков (дыра безопасности — неавторизованный получал 400 вместо 401 и писал запись в
журнал), таймаут финальной записи, созданный слишком рано (любая операция длиннее таймаута
доходила до записи с уже истёкшим контекстом — ровно тот баг, от которого этот контекст и
защищал), и затирание полного кеша частичным результатом с отчётом об успехе.

Причина, по которой это работает: автор правки смотрит на неё изнутри своей же модели того,
как оно должно быть. Свежий читатель видит следствия.

⚠ Замечания второго движка **не принимать на веру**. Проверять по исходнику: часть находок
окажется мимо. Но проверять надо каждую.

## 7. Дисциплина фиксации изменений

- Коммит на модуль, а не на всю кампанию. Диффы на 30 файлов не ревьюются.
- Разделять правку и тесты на два коммита: в сообщении к правке — **почему**, в сообщении к
  тестам — **что именно пинуется**. ⚠ Но только если коммит с правкой собирается сам по себе:
  смена сигнатуры тащит за собой правку вызывающих в тестах, иначе `git bisect` упирается в
  несобирающийся коммит (см. §8).
- ⚠ **Добавлять в индекс только явными путями.** Если в дереве параллельно работает кто-то ещё
  (или другая сессия агента), голая команда «добавить всё» утащит чужой код в ваш коммит.
- В сообщении коммита писать последствие, а не название линтера. «Отменённое задание навсегда
  оставалось в статусе выполняется» полезнее, чем «исправлены замечания contextcheck».

## 8. Грабли инструментов

- ⚠ **Правила анализа помеченных данных выдают по одной находке за раз, и анализ межпакетный.**
  Прогон по одному модулю скрывает то, что видно на всём репозитории; устаревший кеш даёт
  разный результат между запусками. Проверять: очистить кеш → прогон по всему репозиторию →
  повторять, пока число не перестанет падать.
- ⚠ **Линтер «протухшего контекста» срабатывает на любое присваивание пакетной переменной с
  контекстом.** Тест не может подменить глобальный контекст на свой — линтер валит гейт на
  строке присваивания. Либо контекст передаётся параметром, либо подмена делается через
  функцию-хук, но не присваиванием пакетной переменной.
- ⚠ **Коммит, меняющий сигнатуру, обязан нести в себе правку всех вызывающих, включая тесты.**
  Иначе `git bisect` упирается в несобирающийся коммит, и вся история становится
  небинарящейся. Разделять правку и тесты на два коммита можно только тогда, когда первый
  собирается сам по себе.
- ⚠ **Вспомогательная функция «тихо закрыть» ломает специализированный линтер утечек**: он
  распознаёт только буквальный вызов закрытия в месте отложенного вызова. Писать буквально.
- ⚠ **Модернизирующие автоправки бывают ломающими.** Две пришлось закрепить выключенными:
  одна убирает из сериализации поля с нулевым значением (меняет формат ответа), другая
  превращает пустой список в непустой (в сериализации `null` становится `[]`). Фронтенд ломается
  молча. Прежде чем включать пакет автоправок — прочитать список того, что он делает.
- ⚠ **Диагностика языкового сервера в редакторе отстаёт от диска** во время массовых правок
  сигнатур. Не верить ей, верить сборке.
- **Не дублировать анализаторы**: если стандартный набор проверок уже гоняется отдельной
  фазой, внутри линтера включать только недостающие.
- Обновление версии языка откладывать явно и **с записанной причиной**: у нас линтер собран
  предыдущей версией и не разбирает новый синтаксис.

## 9. Чего не делать

- Не выключать правило глобально «пока что». Глобально выключенное правило не включается никогда.
- Не подставлять пустой контекст ради тишины линтера.
- Не закрывать перебор вариантов пустой веткой «иначе».
- Не подавлять правило без причины в самой директиве.
- Не запускать линтер с автоисправлением в гейте.
- Не верить зелёным тестам без проверки мутацией.
- Не параллелить починку модулей, которые меняют сигнатуры друг друга: сборка ломается через
  границы модулей, и агенты начинают чинить чужую работу.
- Не менять форму ответа, коды состояния и имена полей — на них завязан клиент. Обратная
  совместимость важнее красоты.

## 10. С чего начать в разнородном проекте

Порядок для агента, которому это отдают:

1. **Определить стеки по факту наличия файлов-признаков.** Для каждого найденного — минимальный
   набор фаз. Отсутствующий стек не существует.
2. **Собрать гейт** из одной точки входа с двумя уровнями. Замерить каждую фазу, дорогую
   вынести в полный уровень.
3. **Проверить хук**: намеренно сломать код, убедиться, что гейт ругается и не даёт закончить.
4. **Включить строгие правила и померить бэклог целиком.** Не чинить пока ничего. Записать
   число — это точка отсчёта.
5. **Проверить существующие тесты мутацией.** Сломать одну ветку в самом покрытом модуле.
   Результат этой проверки определяет, сколько тестов придётся написать по дороге.
6. **Нарезать очередь по модулям**, оформить исключения поимённо в конфиге линтера, записать
   рядом историю и причины.
7. Дальше — по одному модулю: правка + тесты на затронутые ветки → red-then-green → ревью
   вторым движком → коммит → вычеркнуть модуль из конфига.

Отдельно: **мусор, который нельзя починить, вывести из области анализа явно** и записать почему.
У нас 24 недоделанные одноразовые утилиты вне системы контроля версий давали 145 замечаний из
946 — фикс туда невозможно закоммитить, так что это чистый шум. Из области линтера выведены,
из сборки — нет.
